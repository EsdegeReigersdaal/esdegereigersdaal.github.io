# DataOps architecture

Reviewed **1 October 2026** against `dataops-infrastructure` master at
[`7e504e3`][revision], using its production configuration and dated deployment
evidence. This is a public architecture snapshot, not a live inventory. This
review did not query Azure or read production data. Source links pin that revision
and may require access to the private repository.

The platform has one active infrastructure environment: **production in Azure
North Europe**. OpenTofu owns infrastructure and access declarations; Ansible
configures self-hosted Dagster. The separate `dataops-dagster` repository owns
pipeline code and application releases. Microsoft Fabric consumes publications;
its capacity, workspaces and content are managed outside this infrastructure.

## Ownership

| Owner / layer | Current responsibility |
| --- | --- |
| Data Engineering | Platform operation, Dagster configuration and pipelines |
| Planning & Control and other departments | Analytics and data-product requirements |
| Core (`core/`) | State, CI identities/grants, runner network, ACA Jobs, runner registry/vault and power permissions |
| Network | Platform VNet, subnets, peering, private DNS and network grants |
| ETL | AKS, PostgreSQL, ADLS/native Tables, application registry, ETL vault, workload identities and alerts |
| Ansible | Dagster control services, ingress/authentication, certificates and database initialization |
| `dataops-dagster` | User-code definitions, images, Helm deployment and dataset publication |
| DW compatibility state | Optional existing Fabric capacity identifier; no Fabric resource lifecycle |
| External administration | Fabric capacity/workspaces, Entra application registrations and public DNS |

Core retains its original bootstrap state lineage. The former separate vault
layer and legacy VMSS runners are retired. Compatibility names and source-system
labels such as `testing` do not imply another deployed environment. See
[layer configuration][layers], [delivery ownership][onboarding] and
[Core retirement evidence][ci-audit].

## Runtime and user access

Dagster runs inside a private AKS cluster with three node pools:

| Pool | Configured capacity | Workloads |
| --- | --- | --- |
| System | One `Standard_B2s_v2` node | Kubernetes system services |
| Dagster | One to three `Standard_B2s_v2` nodes | Control services, ingress/authentication and resident user-code server |
| Codeworker | Zero to three `Standard_DC2as_v5` nodes | Dagster run Jobs |

Counts apply while the cluster runs; the power controller can stop the whole
cluster. The source's [consolidation study][consolidation] records the system
pool as a reliability concern requiring separate remediation. It does not
establish that a replacement runtime has been deployed.

The public application path is:

1. A permitted source address connects to NGINX over HTTPS.
2. Internal `oauth2-proxy` authenticates with Microsoft Entra ID and checks
   Data-Engineering group membership.
3. Authorized requests reach the internal Dagster webserver.
4. Webserver and daemon load definitions from the user-code server over internal
   gRPC. The daemon coordinates queued runs and launches Kubernetes Jobs.

Control services live in `dagster-system`; user code and run/step pods live in
`dagster-code`. Ansible configures the Kubernetes run launcher, up to five
concurrent runs and a default execution-pool limit of one. The user-code server
stays on the Dagster pool; run Jobs use the codeworker pool. See
[AKS resources][aks], [Ansible settings][ansible] and [Helm configuration][dagster-values].

The AKS API is private, local accounts are disabled, and Entra RBAC and workload
identity are enabled. Runtime pods exchange projected service-account tokens
for Azure access. Build/deployment identities are separate from runtime identities.

NGINX is the only public application ingress. HTTPS retains source filtering and
Entra authentication; HTTP serves ACME HTTP-01 challenges only. Certbot renews
certificates, with TLS material held in Key Vault and synchronized into Kubernetes.
[SSO deployment evidence][sso] records a successful member login on 21 September.
Denied-user/source tests, MFA/Conditional Access enforcement and group-overage
behaviour remained unverified; this snapshot does not claim those checks passed.

## Storage and data flow

**PostgreSQL holds Dagster metadata.** PostgreSQL 16 Flexible Server uses a
delegated private subnet and private DNS, with public access disabled. Dagster
uses workload identity. The shared server retains its existing mixed Entra/password
authentication and local administrator for compatibility; this is not a runtime
password requirement. The former `diensten_api` database is retired.
See [database resources][postgres].

**Data products use one production storage account.** ADLS Gen2 provides
`raw`, `curated` and `shared` filesystems. Native Azure Tables
`SdbDutyState` and `SdbNachtdienstAuth` hold current-state publications in the
same account. Blob/DFS and Table have distinct private endpoints. Shared Key,
anonymous access and local users are disabled.

Dagster has account-wide Blob Data Contributor access and a separate Table Data
Contributor grant per declared table. The original approved Fabric workspace and
ConfluxDB have account-wide Blob Data Reader access. Filesystem names are usage
conventions, not isolation between these identities. Human Blob reader grants do
not confer native Table access. See [storage resources][lake],
[Table resources][tables] and [additional Fabric grants][fabric-access].

Pipelines call source APIs, then publish files and native Table entities. Fabric
uses existing connections and ADLS shortcuts to consume Delta publications. An
ADLS shortcut does **not** read a native Azure Table:

| Data product | Native destination | Fabric publication in ADLS |
| --- | --- | --- |
| SDB duty state | `SdbDutyState` | `curated/sdb/duty_state_delta` |
| Nachtdienst authorization | `SdbNachtdienstAuth` | `curated/Nachtdienst_auth_table` |

[SDB consumption was verified on 22 September][sdb-fabric].
The [1 October Nachtdienst incident and recovery][nachtdienst] showed that native
Table publication can succeed while separate Fabric output stays stale. The
corrected application publishes both destinations; deployment, the updated
OneLake snapshot and five-column SQL consumption were verified. Direct native
Table readback was not independently performed in that recovery. Deployment
health alone does not prove fresh downstream data.

## Network and security boundaries

The Core-owned runner VNet and Network-owned platform VNet are peered. Private
DNS resolves AKS, PostgreSQL, state Blob, both vaults and lake endpoints for the
appropriate networks. Runner-linked Blob and Key Vault zones include mirror
records for ETL resources. PostgreSQL uses a delegated subnet, not a PostgreSQL
Private Endpoint deployment.

AKS uses Azure CNI and Standard Load Balancer egress
(`outbound_type = "loadBalancer"`). No NAT Gateway or Bastion resource is
declared. The runner environment uses internal load balancing. Both registries
are Basic ACR with authenticated public endpoints, without private registry
endpoints. See [AKS resources][aks] and [runner networking][runner-network].

State storage is private-only. ETL storage and both vaults retain explicit,
temporary public operator firewall exceptions alongside private workload access.
ADLS also permits approved Fabric workspace resource instances. VPN access is
still planned; private endpoints alone do not connect workstations.
See [network resources][network], [production inputs][production] and
[planned access improvements][planned].

Scoped identities and grants are declared, but `retire_legacy_access`,
`retire_legacy_trust` and `retire_legacy_secret_access` remain false in the
reviewed inputs. Replacement grants do not establish removal of older broad
access. See [Core inputs][core-inputs] and [the security model][security].
The latter's older statement that Entra UI authentication is disabled is
superseded by production flags and the 21 September rollout.

## Build and delivery

GitHub hosts the repositories and workflows. Ordinary PR checks use hosted
runners without Azure credentials. An optional `run-plan` label on a
same-repository infrastructure PR requests a backend-backed preview on ACA;
forks receive static checks only.

Ephemeral Container Apps Jobs provide separate runner pools for platform
operations, application deployment and application builds. They scale to zero
and register through GitHub Apps. Privileged jobs use GitHub OIDC and separate
operation identities. ACR Tasks executes archived-source builds, checks and
scans; Docker does not run inside ACA.

The two registries hold images, build caches, SBOMs and OCI release/configuration
bundles. Application handoff uses these bundles instead of GitHub artifacts.
Images are pinned by digest; evidence does not establish the old documentation's
blanket image-signing claim. See [build procedures][ci-storage] and
[rollout evidence][ci-audit].

Infrastructure and Ansible releases are **manual** from `master`. Each
infrastructure release creates and applies a fresh plan in one run. Changed Core
prerequisites precede affected Network, ETL and DW layers. Binary plans are
temporary and are not published as artifacts.

Application delivery can run **automatically** after successful
`dataops-dagster` master CI when enabled. Helm deploys the user-code release.
The application acquires a bounded wake hold through the infrastructure power
workflow, waits for private AKS readiness, deploys/verifies the selected image,
then releases only its own hold. [The 1 October rollout][holds] verified cold
startup, deployment and coexistence with a manual daemon hold.

Platform operations share the infrastructure repository's production queue.
That queue does not span repositories; application deployment holds coordinate
availability. GitHub dispatch access is the operator trust boundary. The
platform does not claim an enforced independent-review gate.
See [delivery procedures][onboarding].

## Availability, monitoring and recovery

The normal schedule uses **Europe/Amsterdam** local time:

| Window | Behaviour |
| --- | --- |
| Daily 23:00-23:30 | Start PostgreSQL and AKS concurrently; prepare services with daemon paused |
| Daily 23:30-06:00 | Run the processing daemon |
| From 06:00 | Pause/drain; stop AKS before PostgreSQL once idle |
| Saturday 06:00-15:00 | Keep compute available for maintenance, daemon paused |
| Manual / deployment holds | Extend availability temporarily; a manual daemon hold can extend processing |

The UI can be offline outside these windows. Queued/active work, unreadable run
state or failed operations defer shutdown. GitHub scheduling is best effort,
so these are operating windows rather than an uptime guarantee. Temporary
operator holds are not permanent schedule changes. See [power operations][power].

Azure Monitor rules cover PostgreSQL CPU, memory, storage and connections, plus
AKS/PostgreSQL resource health. Action-group email, GitHub summaries and on-demand
checks support operations. No centralized application log ingestion/export is
configured; Dagster uses `NoOpComputeLogManager`.
See [monitoring resources][monitoring] and [Helm configuration][dagster-values].

State uses ZRS, Blob versioning and 30-day soft deletion. Data storage uses LRS.
PostgreSQL keeps 14 days of backups; geo-redundant backup is disabled and no
high-availability block is configured. Evidence does not establish multi-region
failover, a completed restore exercise or a recovery-time commitment.
See [state storage][state] and [database configuration][postgres].

## Retired and proposed architecture

Dagster+ Cloud and its agent are absent from the current runtime. Development/
production clusters, NAT-only access, Bastion, private Premium ACR, RA-GRS recovery
and centralized Log Analytics from the old model do not describe this deployment.

The diensten PostgREST/API Management service, separate report database and SQL
roles were retired in September; former ingress paths return HTTP 410. Shared
Dagster PostgreSQL remains. External Entra application objects were outside that
retirement. See [retirement evidence][retirement].

VPN, stronger native GitHub approval controls and VM/Container Apps runtime
consolidation remain proposals. See [planned improvements][planned] and the
[consolidation study][consolidation].
