# ConfluxDB C4

This document provides an overview of the ConfluxDB dataplatform hosted on azure across environments based on the C4 software architecture model

## Level 1 - System Context

### System boundary

- ConfluxDB is the umbrella term for the data platform resources deployed on the Esdege-Reigersdaal tenant. It features components separated by production and development enviroments such as virtual networks, AKS clusters, PostgreSQL databases, Key Vaults, Azure Container Registry, Azure Monitor and Terraform state management.
- ConfluxDB by default rejects all inbound internet traffic at every layer (NSGs, private endpoints,registry firewall). Only outbount connections initiated from AKS workloads traverse the NAT gateway to reach the Dagster+ cloud control plane, Github, Microsoft Entra ID, external data providers and the downstream Data Warehouse.
- Engineers never connect directly to the AKS or ConfluxDB related components. All changes are done through Github Repositories, CI/CD automation and the Dagster+ Control plane. The Terraform repository updates the ACR with new container images to reflect changes coming from new Code Worker or Agent builds while maintaining the outbound-only security posture.
- GitHub hosted runners assume least-privilege Entra ID roles using Federated Identity Management implemented through OIDC. The repository pipelines can push signed images to the Azure Container Registry are are immutable. The pipelines retrieve scoped secrets from the Azure Key Vault and local environment variables are provided through Github Environments.
- The IaC repository pipeline can modify azure resources such as the AKS and create necessary roles according to it's own role assignment.
- In case of emergencies Break-Glass measures can be taken using an Azure bastion host deployed per environment inside of the Virtual Networks. These bastion hosts and the associated role are deployed just-in-time using the IaC repository to provide emergency access to psql sessions without violating the security principals such as least privilege and outbound only traffic.

### External actors and systems

- Data Engineers push pipelines to the ConfluxDB code worker repository on Github and monitor runs via the Dagster+ Cloud control plane.
- The Planning & Control team consumes data pushed towards the Data Warehouse and request new or adjusted pipelines from the Data Engineers when new data sources are required.
- Site Reliability Engineers maintain the IaC repository, execute terraform changes and reconcile production and development as well as supporting services. Site Reliability Engineers also drive incident response by coordinating changes in the repositories when pipelines or infrastructure degrade.
- External Data Providers receive outbound Meltano extraction calls that query API's for data. These API's include but are not limited to REST API's, databases, CSV files and .xlsx files. All integrations are initiated from inside the platform.
- The Dagster+ Cloud (SAAS) control plane orchestrates jobs and communicates with the Dagster Agent running inside AKS over outbound HTTPS using polling.
- Github hosts the Code Worker, Dagster Agent, IaC repository and the bootstrap backend repository. Github provided Ubuntu runners execute action workflows and obtain ephemeral Azure credentials through OIDC federation and interact with the Azure Container Registry over its public endpoint.
- Microsoft Entra ID (Azure AD) authenticates users and applications, issues workload identities for AKS and GitHub Actions. Entra ID is managed by the IT department.
- External Data Warehouse is an Azure SQL (MSSQL) server owned by the Planning and Control team, operating in the same tenant but a separate network. Code Worker loads curated datasets into it over outbound TLS connections, using firewall rules that accept the NAT gateway's egress addresses only.
- Power BI Service (SaaS) hosts semantic models and dashboards for the Planning & Control Team, authenticating users via Microsoft Entra ID and connecting to the external Data Warehouse through the organisation's managed data gateway. Dataset refresh operations remain under the Planning & Control team's remit and sit outside the ConfluxDB platform scope.

### High-level data flow

1. Dagster+ Cloud schedules a run and signals the Dagster Agent inside AKS.
2. The Dagster Agent pulls image digests from Azure Container Registry and launches the ConfluxDB Code Worker pod for the run.
3. The Code Worker retrieves secrets from the environment-specific Key Vault, authenticates to external data providers, gathers raw data via Meltano, stores it in PostgreSQL raw schemas, transforms it with SQLMesh, and publishes curated tables both in PostgreSQL curated schemas and in the external Data Warehouse (MSSQL).
4. GitHub Actions pipelines run on GitHub-hosted Ubuntu runners, authenticate to Azure using per-repository OIDC, push signed images to Azure Container Registry via its public endpoint, and notify the infrastructure repository to update AKS image hashes via Terraform plans. Terraform applies run within the same outbound-only constraints, ensuring no inbound rules are introduced.
5. Planning & Control Team queries the curated datasets through Power BI dashboards backed by the external Data Warehouse, then provide backlog input to Data Engineers for new pipeline development.

## Level 2 - Container View

### Environment and connectivity

- Development and production environments live in the same tenant but run in fully separate Azure virtual networks, AKS clusters, PostgreSQL instances, Key Vaults, and Terraform workspaces. They share the centrally managed Azure Container Registry yet maintain isolation through network segmentation, scoped identities, namespaces, and GitHub Environments.
- Each environment-specific virtual network hosts dedicated subnets for AKS and PostgreSQL. Outbound internet access is forced through that environment's NAT Gateway. Inbound connectivity is denied by default via Network Security Groups. Private endpoints couple each AKS cluster with its respective PostgreSQL instance and Key Vault, and surface Azure Container Registry privately to the clusters even though the registry itself remains an Azure-managed service outside the VNets.
- DNS for private endpoints is handled through environment-specific records within a shared Azure Private DNS zone, allowing AKS pods to resolve Azure Postgres and Key Vault URLs without traversing public DNS.
- GitHub  runners remain outside the VNets and reach Azure control planes (ACR, AKS, Key Vault) over public endpoints secured with short-lived OIDC-issued tokens whose permissions are limited to image publishing, secret retrieval, or Terraform-managed changes depending on the repository.

### Identity and secret management

- Microsoft Entra ID provides SSO for engineers and issues managed identities for AKS workloads. Workload identities are scoped per namespace/environment to limit blast radius.
- Each environment owns a dedicated Azure Key Vault. Runtime secrets (database credentials, external provider keys, Dagster tokens) are segregated per vault, with access policies restricted to their matching managed identities and GitHub service principals.
- GitHub Actions uses OIDC federation per repository (Code Worker, Dagster Agent, Terraform). The application repositories assume roles that can push signed images to Azure Container Registry and retrieve explicit secret sets from Key Vault; the Terraform infrastructure repository assumes a separate role empowered to update AKS, networking, and other Azure resources while remaining bound by resource-group scope and policy guardrails.
- Terraform modules manage secret lifecycle by minting new Key Vault versions, revoking superseded credentials, and codifying rotation cadence. Emergency access follows controlled click-ops or the IaC Backend repository's break-glass workflow so that changes remain auditable.
- Operational break-glass sessions are executed through Azure Bastion with Defender for Cloud just-in-time (JIT) policies, issuing short-lived local administrator credentials stored in Key Vault and enforcing post-incident audit sign-off.

### Network security and trust controls

- Network Security Groups block all unsolicited inbound access to Virtual Network components while allowing minimal horizontal flows (AKS to PostgreSQL / Key Vault / Private Endpoints). Diagnostic logs stream to Azure Monitor for uptime verification and logging.
- Azure Container Registry publishes private endpoints for AKS image pulls while retaining a hardened public endpoint for the Github runners. Registry firewall rules allow only the required Microsoft Service tags, anonymous access is disabled and content trust with Microsoft Defender for cloud policy assignments enforces signed and immutable images.
- The NAT gateway publishes the only outbound IPs used for SAAS interactions (Dagster+ Cloud, GitHub, external data providers, external Data Warehouse). Allow lists on those services reference the NAT egress addresses only, while GitHub runners rely on Azure RBAC and signed requests rather than inbound allow lists.
- Azure control planes that cannot be privately linked (AKS API server, Azure Container Registry management endpoint, Key Vault management plane) remain exposed through Microsoft-managed public endpoints but are callable only by identities issued through the federated OIDC roles and subject to Azure RBAC, Conditional Access, and Defender for Cloud policy enforcement.
- Terraform applies run on GitHub runners as well, Azure Policy deny assignments and Terraform guardrails block any attempt to create load balancers, public IPs, or inbound rules, preserving the outbound-only boundary.

### Supporting platform services (Azure-managed)

These Azure-managed services provide networking, data, and security capabilities that underpin the application containers without running custom code.

#### Azure Virtual Network

Provides isolated networking with CIDR ranges aligned to corporate standards. Each environment owns its own VNet with dedicated subnets for AKS and PostgreSQL, segregated route tables, enforced egress through the corresponding NAT Gateway, and private DNS integration for internal name resolution without cross-environment peering.

#### Azure NAT Gateway (Egress Only)

Supplies static outbound IP addresses for AKS node pools and supporting PaaS services. Each environment operates its own gateway so that allow lists on Dagster+ Cloud, GitHub, external data providers, and the downstream Data Warehouse can differentiate dev and prod egress. Gateways attach to dedicated egress subnets, are deployed in zone-resilient configurations, and depend on network security groups to block unsolicited return flows.

#### Network Security Groups

Environment-specific NSGs protect database and AKS subnets, permitting only required east-west flows (AKS to PostgreSQL/Key Vault) and blocking all unsolicited inbound access. Rules explicitly deny cross-VNet traffic, and flow logs stream into Azure Monitor for auditability.

#### Azure Private DNS Zone

Hosts records for PostgreSQL, Key Vault, and other private endpoints. Zone links attach individually to each environment VNet so AKS workloads resolve services privately without exposing records publicly.

#### Azure Kubernetes Service (AKS)

Two independent clusters (dev and prod) run the Dagster Agent and Code Worker workloads from separate VNets. Clusters authenticate to Key Vault via managed identities, pull container images from Azure Container Registry, and receive new image digests through Terraform-managed manifests updated by GitHub Actions. Nodes run without public IPs; Kubernetes Pod Security Admission (restricted profile), Azure Policy assignments, and namespace-scoped network policies enforce the outbound-only communication model. Critical system node pools are deployed across availability zones where the region supports them.

#### Azure Database for PostgreSQL (per environment)

Holds raw landing tables, staging schemas, curated datasets, and the shared pipeline metadata schema for the platform. Meltano ingests data into raw schemas and persists loader checkpoints in the metadata schema, SQLMesh stores its state tables and plan snapshots alongside model/production schemas, and materialised outputs may be exported to the external Data Warehouse. Automated backups, point-in-time restore, and geo-redundant backup storage support disaster recovery, while alerting policies surface capacity and replication issues early.

#### Azure SQL Database (Data Warehouse)

Downstream MSSQL server managed by the Analytics team in a separate network. Receives curated exports from the Code Worker through outbound TLS connections from AKS. Firewall rules restrict ingress to the NAT Gateway egress addresses; no reverse connectivity into the ConfluxDB VNets is permitted. An organisation-managed Power BI data gateway inside the Analytics network brokers queries from Power BI Service without exposing inbound paths toward ConfluxDB infrastructure.

#### Power BI Data Gateway (Organisation-managed)

Provides the bridge between Power BI Service and the external Data Warehouse. The gateway runs in the Analytics team's network, authenticates via Microsoft Entra ID, and only initiates outbound connections to Power BI Service. High-availability pairs are configured to avoid reporting outages while keeping the ConfluxDB VNets isolated.

#### Azure Container Registry

Stores container images for the Dagster Agent and Code Worker. Images are tagged per environment; GitHub Actions promote validated images from development to production and emit events that trigger IaC pipelines to update deployment descriptors. Private endpoints expose the registry to AKS, while GitHub-hosted runners push via the public endpoint using OIDC-issued tokens. Firewall rules permit AKS subnets and the GitHub Actions service tags, and content trust enforces signature verification before pull. Cross availability zone replication and image retention policies ensure continuity if a region fails and prevent stale or unsigned artifacts from lingering.

#### Azure Key Vault (dev/prod)

Separate vault per environment storing secrets, certificates, and connection strings. Access policies and RBAC assignments restrict usage to the corresponding AKS managed identities and GitHub OIDC principals. Purge protection, soft-delete, and secret versioning are enabled to support auditable rotation and recovery.

#### Azure Monitor and Log Analytics

Collects metrics, logs, and alerts for AKS, PostgreSQL, Key Vault, and CI/CD. Container Insights delivers pod-level telemetry, while alert rules route to Azure Monitor action groups tied to the organisation's operations on-call schedules. Dashboards aggregate Dagster run metadata, Terraform apply outcomes, and Azure platform health so Platform Engineers can triage incidents from a single pane of glass. This managed service underpins the Azure Monitor Telemetry Adapter described in the Level 3 component views.

#### Azure Bastion (Break-glass Jump Host)

Provides the hardened jump-host capability inside each environment VNet. Just-in-time access policies require Platform Engineers to request time-bound sessions. Bastion exposes SSH/RDP over the Azure portal without public IPs, strictly limits sessions to audited kubectl/psql diagnostics, and integrates with Key Vault for ephemeral credential distribution.

#### Azure Storage Account (Terraform State)

Maintains remote Terraform state containers and locking blobs. Scoped access is granted only to Terraform service principals through RBAC. The account uses zone-redundant storage with RA-GRS replication, and diagnostic logs integrate with Azure Monitor to track state changes.

### Resilience and disaster recovery

- **Data services**: PostgreSQL uses geo-redundant backups and point-in-time restore. Azure SQL Database failovers and policies are managed by the Planning & Control team.
- **Container runtime**: AKS system node pools span availability zones and uses blue green deployment  to roll images published without downtime.
- **Control plane artefacts**: Azure Container Registry and the Terraform state storage rely on RA-GRs so that image pulls and infrastructure state stay available during regional incidents.
- **Secrets and configuration**: Key Vault purge protection plus Terraform-managed rotation ensure credentials can be recovered quickly while preventing accidental deletion during incident response.
- **Operational response**: Azure Monitor action groups notify Platform Engineers, who perform triage via repositories and the Azure Bastion for AKS diagnostics.

### Application containers

These containers execute within AKS or the adjacent control plane to deliver the ConfluxDB data pipelines.

#### Dagster Agent

Runs inside AKS, authenticates to Dagster+ Cloud using environment-specific credentials from Key Vault, and launches Code Worker pods. It emits run metadata and logs to both Dagster+ Cloud and Azure Monitor.

#### ConfluxDB Code Worker

Executes Meltano extractors, SQLMesh transformations, and publish steps. It consumes secrets from Key Vault, interacts with PostgreSQL for raw, curated, and metadata schemas (capturing Meltano checkpoints and SQLMesh state tables), and performs outbound loads to the Data Warehouse. Telemetry and run metadata are streamed to Azure Monitor.

#### Dagster+ Cloud Control Plane

SaaS orchestration plane that schedules jobs, stores run history, and communicates with the Dagster Agent over outbound HTTPS. Separate agent tokens keep dev and prod isolated. Dagster+ Cloud also persists asset lineage, freshness policies, and ownership metadata referenced by the Asset Metadata and Governance Service.

### DevOps tooling

The DevOps toolchain coordinates image builds, infrastructure changes, and repository management across environments.

#### GitHub Version Control and Actions

Hosts the Code Worker, Dagster Agent, and Terraform repositories. Actions workflows run on GitHub-hosted Ubuntu runners, authenticate to Azure via per-repo OIDC trust relationships, build and push container images to Azure Container Registry, and dispatch events or pull requests to the IaC repository when image digests change. The Agent and Code Worker pipelines share an identical pattern: build the image, publish it to the registry, emit a `dagster-agent-image-published` or `worker-image-published` repository dispatch, and let Terraform reconcile AKS manifests with the new digests. Audit logging is enabled for compliance tracking.

#### ConfluxDB Code Worker Repository

Contains application code, Meltano configuration, SQLMesh models, and reusable connector adapters. Successful pipelines produce signed container images and metadata that feed Terraform updates.

#### Dagster Agent Repository

Defines the Dagster Agent image, Helm manifests, and sensor logic required for registration with Dagster+ Cloud. CI workflows build images, push to Azure Container Registry, and notify IaC of new digests.

#### Terraform Infrastructure Repository

Owns infrastructure-as-code for networking, AKS, PostgreSQL, Key Vault, Azure Monitor, and supporting resources. Terraform plans run in GitHub Actions; Platform Engineers review and approve applies. Repository-dispatch triggers (`worker-image-published`, `dagster-agent-image-published`) carry the newly built tags so Terraform can update AKS deployments with the correct Code Worker and Agent digests while preserving inbound restrictions in NSGs and load balancers. Modules are split per Azure component (networking, AKS, registries, observability) to keep scopes minimal and enable targeted policy assignment reviews, and the workflows codify Key Vault secret rotation cadence alongside infrastructure changes.

#### Terraform Backend Repository

Bootstraps Terraform remote state storage, defines IAM role assignments, and maintains separation between dev and prod workspaces. It also provisions service principals used by other repositories' OIDC relationships and documents the click-ops break-glass procedure when emergency access to secrets is required.

### Container interaction summary

- The Dagster Agent and Code Worker pods inside each AKS cluster resolve DNS records and reach their environment-specific PostgreSQL and Key Vault private endpoints over the corresponding environment VNet. Secrets flow back through the managed identity integration before data pipelines write to raw, curated, and metadata schemas (housing Meltano checkpoints and SQLMesh state tables).
- When pipelines need to call external SaaS services (Dagster+ Cloud, GitHub API, upstream data providers, downstream Data Warehouse), traffic egresses AKS through the NAT Gateway, presenting the static IPs that those services allow-list.
- GitHub Actions workflows authenticate with Microsoft Entra ID via OIDC, push images to Azure Container Registry, and emit repository-dispatch events that the Terraform infrastructure pipeline consumes to refresh AKS deployment manifests with the new image digests.
- Terraform plans authenticate with Azure using the same OIDC pattern, lock state in the Terraform Storage Account, and call the AKS API server to apply updated manifests, while Azure Monitor subscribes to diagnostic streams from AKS, PostgreSQL, Key Vault, and the NAT Gateway for observability and compliance evidence.
- External data providers and analytic consumers (Power BI) remain outside the ConfluxDB team boundary and are modelled as variable outbound dependencies.

## Level 3 - ConfluxDB Code Worker Component View

### Component overview

- Run Orchestration Adapter: Receives job context from the Dagster Agent (over Dagster gRPC/API), initialises execution graphs, and coordinates retries and sensor feedback.
- Secret and Configuration Broker: Uses the pod's managed identity to request credentials from the environment's Key Vault (database passwords, API tokens, external warehouse credentials) and injects them into runtime configuration for downstream components.
- Meltano Extractor Runtime: Hosts Meltano plugins and connector adapters defined in repository YAML. It authenticates to external data providers, issues outbound API/DB calls, and writes raw responses into PostgreSQL raw schemas with metadata columns for lineage and load tracking.
- Staging and Validation Services: Applies lightweight schema validation, deduplication, and quality checks on raw tables using SQL-based rules. Failures bubble up to the Run Orchestration Adapter for alerting through Dagster and Azure Monitor.
- SQLMesh Transformation Engine: Compiles SQLMesh models, manages data versioning, and materialises transformed datasets into PostgreSQL curated schemas. It coordinates dependency ordering and maintains incremental runs using metadata tables in PostgreSQL.
- Curated Publisher: Exports final datasets to the external Data Warehouse (Azure SQL / MSSQL) via outbound TLS connections, leveraging stored procedures or bulk copy operations. It also signals Dagster about publication status and updates lineage records.
- Asset Metadata and Governance Service (Dagster+ Cloud): Publishes Dagster asset metadata for every model, capturing lineage, freshness policies, data quality status, and ownership inside the Dagster+ Cloud control plane so Platform and Data Engineers can audit downstream impacts without deploying additional in-cluster components.
- Azure Monitor Telemetry Adapter: Emits structured logs, metrics, and traces to Azure Monitor and Log Analytics, tagging runs with Dagster run IDs and dataset identifiers for cross-system visibility.

### Component interactions

1. Dagster Agent triggers a run; the Run Orchestration Adapter starts execution and requests secrets from the Secret and Configuration Broker.
2. The Meltano Extractor Runtime pulls connectors and ingests data into PostgreSQL raw schemas through the NAT-restricted private endpoint.
3. Staging and Validation Services cleanse the raw data, logging issues to the Azure Monitor Telemetry Adapter and raising failures back to the orchestration logic when thresholds are breached.
4. SQLMesh Transformation Engine materialises models, writing curated outputs into PostgreSQL and updating run state tables.
5. The Curated Publisher loads curated datasets into the external Data Warehouse (MSSQL) and confirms success to the orchestration adapter, which notifies Dagster+ Cloud.
6. Azure Monitor Telemetry Adapter continuously streams logs and metrics to Azure Monitor, enabling real-time dashboards and alerts.

## Level 3 - Dagster Agent Component View

### Component overview

- Deployment Manifests: A Helm chart and Kubernetes YAML definitions describe the AKS namespace, service account, Pod Security Admission settings (restricted), and deployment object that runs the Dagster Agent. Image digests are supplied by Terraform, ensuring the manifest always references the latest signed image.
- Agent Dockerfile: Builds on the hardened Dagster base image, adds organisation-specific sensors, configures outbound-only network policies, and sets the entrypoint for the Dagster agent process. The Dockerfile is rebuilt by GitHub Actions whenever code changes land on the repository.
- Credentials Bootstrapper: At pod start, the managed identity retrieves the environment-specific Dagster agent token and Key Vault references, mounts them as projected volumes, and configures the agent runtime.
- Run Relay and Health Probes: The agent maintains outbound gRPC/WebSocket sessions with Dagster+ Cloud, exposes only internal liveness/readiness probes, and forwards run metadata to Azure Monitor via the cluster logging add-on.
- Image Promotion Hooks: Repository dispatch events publish the new agent digest to the Terraform repository so that AKS deployments and DaemonSets converge on the updated image without downtime.

### Component interactions

1. The Terraform plan applies the latest Helm values, substituting the image digest supplied by the GitHub Actions pipeline.
2. AKS pulls the signed image from Azure Container Registry over the private endpoint and instantiates the Dagster Agent pod.
3. On start, the agent contacts Key Vault via the managed identity to retrieve connection secrets, then establishes an outbound session with Dagster+ Cloud.
4. Dagster+ Cloud assigns jobs to the agent; it schedules Code Worker pods, monitors progress, and emits structured logs to Azure Monitor.
5. Health probes and metrics feed Azure Monitor alerts, allowing Platform Engineers to detect scheduling or connectivity regressions quickly.

## Level 3 - Terraform Infrastructure Component View

### Component overview

- Core Networking Module: Defines the environment-specific virtual networks, subnets, NAT gateways, network security groups, route tables, and private DNS zones. Deny-by-default NSG rules and Azure Policy assignments enforce the outbound-only posture.
- Data Layer Module: Provisions Azure Database for PostgreSQL instances, firewall rules limited to VNet integration, private endpoints, and alert rules. Outputs expose connection strings consumed by the Code Worker.
- Cluster Module: Configures AKS (node pools, managed identities, Pod Security Admission enforcement) and integrates it with Azure Monitor, Container Insights, and the private Azure Container Registry endpoint.
- Registry and Secrets Module: Creates the Azure Container Registry, enables content trust, restricts the firewall to AKS subnets and GitHub Actions service tags, configures scoped role assignments, and provisions environment-specific Key Vaults with RBAC policies for AKS and GitHub Actions principals.
- Observability Module: Sets up Log Analytics workspaces, diagnostic settings for all services, and alert routing to operations teams.

### Delivery workflow

1. GitHub Actions receives a repository-dispatch event from the Code Worker or Dagster Agent pipeline containing the new image digest.
2. The Terraform pipeline authenticates to Azure using OIDC, locks remote state in the Storage Account, and plans the module updates (typically an AKS deployment digest change).
3. Platform Engineers review the plan output; once approved, the apply executes within the sandboxed runner that has no inbound connectivity.
4. Terraform updates AKS manifests with the supplied digest, confirms that NSGs and firewall baselines remain unchanged, and emits state-change logs to Azure Monitor.
5. Completed applies notify downstream stakeholders (Data Engineers, Platform Engineers) through repository status checks so they know the new image is live.
